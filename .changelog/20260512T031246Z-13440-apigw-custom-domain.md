- `infra/dev/api-gateway-domain`: new Terraform module that provisions the public custom domain wiring for the dev HTTP API at `api.dev.panakoes.com`. Creates a DNS-validated `aws_acm_certificate` in us-east-1 (cert region must match the HTTP API region for HTTP API v2; this differs from CloudFront, which always pulls from us-east-1 regardless of the distribution region) and two gated resources (`aws_apigatewayv2_domain_name` + `aws_apigatewayv2_api_mapping`) that attach the custom domain to the existing `panakoes-dev-public` HTTP API stage from `infra/dev/api-gateway/`. Apply is two-phase because DNS for `panakoes.com` is authoritative on Cloudflare (registered 2026-05-07) and this Terraform run does not have Cloudflare API credentials: phase 1 applies with `enable_domain_mapping = false` to provision ONLY the cert; Phil reads the `certificate_validation_records` output, adds the `_xxx.api.dev` CNAME to Cloudflare with proxy status set to DNS only (the Cloudflare proxy blocks ACM from resolving the record), waits 5 to 30 minutes for ACM to flip the cert from `PENDING_VALIDATION` to `ISSUED`, then re-applies with `enable_domain_mapping = true` to materialize the regional domain endpoint (`d-xxx.execute-api.us-east-1.amazonaws.com`) and the stage mapping. Phil then adds the second Cloudflare CNAME (`api.dev` to the regional domain, DNS only) and the custom URL answers. The default `n2un8ica69.execute-api.us-east-1.amazonaws.com` invoke URL keeps working alongside the custom domain. `services/admin/src/lib/config.ts` `VITE_API_BASE_URL` default is intentionally NOT changed in this PR; that flip is a follow-up after Phil verifies the custom URL answers 200 from his browser. `infra/dev/api-gateway-domain/README.md` documents the full five-phase apply ritual + the two Cloudflare records + the `curl` verification. `infra/README.md` updated with the new module entry.
