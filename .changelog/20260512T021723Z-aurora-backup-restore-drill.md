Cloned the source cluster via `restore-db-cluster-to-point-in-time` (`--use-latest-restorable-time`) to `panakoes-dev-auth-restore-test-20260511220317`, stood up a `db.serverless` writer (~14 min wall clock to both `available`), ran a one-off Fargate task (`panakoes-restore-drill-probe`) executing `SELECT COUNT(*) FROM "user"` from `public.ecr.aws/docker/library/postgres:16-alpine` against the restored endpoint over the existing dev VPC SG, confirmed `row_count = 1` matching a same-shape probe against the production cluster, then deleted the test instance + cluster (`--skip-final-snapshot` permitted on the throwaway clone only) and deregistered both probe task definitions. Total drill cost under $0.10; total wall clock ~30 minutes. Pre-flight findings: AWS Backup `panakoes-dev` vault holds 6 DynamoDB recovery points and 0 Aurora recovery points (the dev backup plan in `infra/dev/backup/main.tf` selects only the three DynamoDB tables, so Aurora recovery currently flows through native PITR rather than AWS Backup; the runbook flags this gap and the follow-up to add the cluster ARN to `aws_backup_selection.resources`). Aurora native PITR confirmed healthy: retention 7 days, `LatestRestorableTime` within 1 minute of wall clock, `EarliestRestorableTime` 2026-05-10T05:56Z. Master-password rotation timing validated against the PITR window: `panakoes-dev/postgres-auth-db-password` last changed 2026-05-09T16:20 (predates earliest restorable), so the current secret value decrypts the restored cluster's catalog correctly. Disaster scenarios covered by the drill: accidental DROP / DELETE without WHERE, ransomware row tampering within the 7-day window, schema-migration corruption. Not covered: account compromise, us-east-1 region outage, pre-PITR-window corruption (follow-ups: cross-region AWS Backup copy to us-west-2, cross-account vault copy for prod, add Aurora to the AWS Backup selection).
