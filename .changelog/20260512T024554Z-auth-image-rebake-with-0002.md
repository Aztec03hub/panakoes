- `infra/dev/ecs` + `services/auth`: rebaked the auth runtime image from current main HEAD (tag `migrate-<sha>`, image digest `sha256:<image-digest>`, multi-arch `linux/amd64,linux/arm64`) and bumped `var.auth_image_tag` default in `infra/dev/ecs/variables.tf` from `migrate-8c90ace` to `migrate-<sha>`. The prior `migrate-8c90ace` build predates PR #232's merge of `services/auth/drizzle/0002_add_session_revoked_at.sql`, so `scripts/run-auth-migration.sh --task-definition panakoes-dev-auth:<rev>` against it could only iterate the two pre-existing migrations (`0000_initial.sql`, `0001_add_role.sql`) and silently skipped the 0002 file (the image filesystem did not contain it). PR #240 surfaced that gap during the post-merge migration run. Rebake procedure: `aws ecr get-login-password ... | docker login ...` against the dev registry, `docker buildx build --builder multiarch --platform linux/amd64,linux/arm64 -f services/auth/Dockerfile -t .../panakoes-dev-auth:migrate-<sha> --push services/auth`, `terraform apply -target=aws_ecs_task_definition.auth` in `infra/dev/ecs` registered revision `panakoes-dev-auth:4` (the targeted apply was necessary because the module state contains pending `ingestion-api` + `query-api` resources from prior PRs that are intentionally NOT applying yet; a non-targeted apply would have created two new ECS services out of scope for this PR), `aws ecs update-service ... --force-new-deployment` rolled the service to revision 4 (stabilized in ~minute, 1/1 running, single deployment), and a final `scripts/run-auth-migration.sh --task-definition panakoes-dev-auth:4` run logged `0000_initial.sql migration_skipped`, `0001_add_role.sql migration_skipped`, `0002_add_session_revoked_at.sql migration_applied`, `migration_run_complete: 1 applied, 2 skipped` (exit 0). The `panakoes-dev/database-url` Secrets Manager secret was temporarily swung to master `panakoes_auth` creds for the DDL run (the runtime `auth_app` role lacks `ALTER TABLE` privilege) and immediately reverted to the prior auth_app version `018b9a94-dbc6-4e80-a419-63189eda21ac` post-migration; revert verified by re-fetching AWSCURRENT and confirming the DSN's user component is `auth_app` (sha256 `1085e297767ec451ed101bde090eac10c6b1c93d1116dd67ad90226877000b09`). Revocation E2E verified against the live dev API Gateway: `POST /v1/auth/sign-in` 200 in 454ms (`role: "admin"`), `GET /v1/auth/auth/me` with bearer 200 in 126ms (user object with admin role), `POST /v1/auth/sign-out` 204 in 125ms, `GET /v1/auth/auth/me` with the now-revoked bearer 401 in 101ms with `{"error":"invalid_token","reason":"session_revoked"}` (confirming PR #232's `revoked_at IS NOT NULL` check is firing against a real-world session row). Rollback: set `var.auth_image_tag` back to `migrate-8c90ace`, `terraform apply -target=aws_ecs_task_definition.auth` in `infra/dev/ecs`, `aws ecs update-service ... --task-definition panakoes-dev-auth:3 --force-new-deployment` (the 0002 column stays in place since the migration is purely additive).
