- `services/auth`: shipped the Better-Auth email-verification flow on sign-up. `POST /sign-up` now issues a single-use verification token (`crypto.randomBytes(32).toString('hex')`, persisted in the existing `verification` table with `identifier=email`, `value=token`, `expires_at=now()+1h`) and dispatches a verification email via AWS SES from `noreply@lafayettelabs.com` (reply-to `phil@lafayettelabs.com`) using `@aws-sdk/client-ses` directly (NOT through `services/notification`; the verification email is synchronous-best-effort and has its own IAM surface on the auth task role). The new `GET /v1/auth/verify-email?token=<token>` endpoint looks the row up, rejects on missing / expired tokens (400 + minimal HTML), and on success flips `user.email_verified=true`, deletes the row (single-use, replay returns 400), and returns an operator-grade HTML page ("Email verified. You can close this tab and sign in."). Expired rows are garbage-collected on hit. The JWT minted by both `/sign-up` and `/sign-in` now carries `email_verified` (boolean, defaults to false on absent claim so legacy / forged tokens cannot grant verification implicitly), and `/validate` + `/auth/me` surface the server-trusted value. v0.1 non-enforcement: sign-in is NOT blocked when `email_verified=false`; downstream services enforce per-route. A future ADR-XX will flip the auth service to deny sign-in on unverified accounts. Sign-up does NOT fail when SES rejects the send (best-effort dispatch; the user row is still created and a resend endpoint lands in a follow-up). New `services/auth/src/auth/email.ts` exposes `VerificationEmailSender` (real SES + in-memory capture) so tests inject a deterministic sender; `services/auth/src/auth/verify-email.ts` owns token issuance + the redemption route. Integration tests (`services/auth/tests/integration/verify-email.test.ts`) cover happy path, token expired (+ GC), token missing / unknown / empty, single-use replay rejection, sign-up best-effort dispatch when SES throws, and the rendered email body. Config gains `EMAIL_VERIFICATION_BASE_URL`, `EMAIL_VERIFICATION_TTL_SECONDS`, `SES_FROM_ADDRESS`, `SES_REPLY_TO_ADDRESS`, `SES_REGION`, and `EMAIL_SENDER_MODE` (`ses` | `disabled`) with safe defaults. `infra/dev/iam/main.tf` grants the `panakoes-dev-auth-task` role `ses:SendEmail` / `ses:SendRawEmail` scoped via the `ses:FromAddress` condition to `*@${var.ses_sending_domain}` (same scoping pattern as the notification policy; SES does not expose per-identity ARN authz on SendEmail). New dependency: `@aws-sdk/client-ses@3.658.1`. SES deliverability dependency: the `lafayettelabs.com` domain is still pending DKIM verification (PR #265, Cloudflare DNS records propagating) and the AWS account is in SES sandbox mode in us-east-1 (sends only to verified recipients until production-access is requested); the verified-single-address sender path works pre-DKIM but mail to arbitrary recipient addresses requires the sandbox exit. `services/auth/README.md` documents the new endpoint, the v0.1 non-enforcement policy, and the SES dependency.
