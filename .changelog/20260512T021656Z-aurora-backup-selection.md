- `infra/dev/backup`: added the Aurora Serverless v2 auth-db cluster ARN to the `aws_backup_selection` resource list so AWS Backup takes daily + monthly snapshots of the cluster into the `panakoes-dev` vault on top of native Aurora PITR (7-day window). Closes the gap surfaced by the PR #282 restore drill, which validated native PITR but found zero Aurora recovery points in the AWS Backup vault because the cluster was not in the selection. New `data.terraform_remote_state.auth_db` lookup in `infra/dev/backup/data.tf` pulls the cluster ARN from `dev/auth-db/terraform.tfstate`; new `local.protected_cluster_arns` + `local.protected_resource_arns` keep DynamoDB and Aurora protected-resource lists separated for readability while concatenating them into the single `resources` argument the selection requires. The selection's logical name stays `panakoes-dev-dynamodb` so the rename does not compound the replacement. IAM is unchanged: the existing `panakoes-dev-backup` service role's attached `AWSBackupServiceRolePolicyForBackup` managed policy already grants `rds:CreateDBClusterSnapshot`, `rds:DescribeDBClusters`, `rds:DescribeDBClusterSnapshots`, and `rds:DeleteDBClusterSnapshot`, so no fresh permissions are introduced. `terraform plan` shows 1 add + 1 destroy on `aws_backup_selection.dev`; the destroy is the AWS-Backup-API replacement requirement for changes to the `resources` argument (the resource has no in-place update path) and removes only the selection-rule association, not any recovery points already in the vault. The Aurora cluster does not need a new `Backup = enabled` tag since the selection matches it by explicit ARN (the tag-selection block continues to apply as a secondary, additive mechanism for future tag-based onboarding). `infra/dev/backup/README.md` updated to call out the Aurora cluster in the protected-resource list and reference the PR #282 drill as the trigger.
