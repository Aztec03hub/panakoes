## [Unreleased]

### Fixed
- `scripts/run-auth-migration.sh`: hardened the one-off ECS migration wrapper after two bugs surfaced during the auth-db first-deploy. (1) `printf '--- begin container logs ...'` and `printf '--- end container logs ---'` errored with `printf: --: invalid option` on GNU `/usr/bin/printf` because the format string started with `--`; the banner lines were silently dropped. Replaced both call sites (and audited every other `printf` in the file) with a `log()` helper that always invokes `printf '%s\n' "$*"`, which is option-parser-safe and `%`-safe. (2) The script discovered the task definition from the running ECS service, but the auth service uses `lifecycle.ignore_changes = [task_definition]` so it stayed pinned to an older revision while a fresh `terraform apply` registered a newer revision carrying `dist/migrate.js`; the older revision was deactivated and AWS returned `InvalidParameterException: TaskDefinition is inactive`. Added a `--task-definition <td>` CLI flag and a matching `TASK_DEFINITION` env var that override the discovered revision (flag wins over env); service-discovery remains the default fallback. Additional hardening bundled into the same change: `AWS_PROFILE` unset now exits 2 with an explicit "AWS_PROFILE is required" message before any AWS call (previously surfaced as a less specific credential error from the AWS CLI); the startup polling loop now logs a `WARN` if the task lingers in `PROVISIONING` or `PENDING` for more than 60s (common symptom of a cold ECR cache on first deploy or a stuck ENI attach); `--help` flag prints usage. New smoke test runner at `tests/scripts/run_auth_migration_smoke.sh` covers all of: `--help` exits 0, missing `AWS_PROFILE` exits 2 with the clear message, unknown flag exits 2, `--task-definition` without a value exits 2, the safe `printf '%s\n'` form does not error on messages starting with `--`, and (via a mock `aws` CLI on `PATH`) the env var override, the flag override, and the service-discovery fallback all resolve to the correct task definition before `run-task` is invoked. `docs/runbooks/auth-db-first-deploy.md` step 12.3 (routine migration) updated to reflect that the `--task-definition` override is now first-class rather than a tracked follow-up.

### Added

The hook now wraps `make ci-pr` (or `make ci-local` as fallback) in `timeout ${_PREPUSH_TIMEOUT_S:-480}` so it can never exceed github.com's ~15-minute SSH idle-timeout mid-push; on budget exhaustion it surfaces the explicit message "pre-push ci-pr exceeded 8min budget; relying on server-side CI. All 103 vitest tests pass. localStorage chosen over httpOnly cookies for v0.1 because the SPA is fully static (no SvelteKit server adapter), making cookies impractical without an extra session-broker service; trade-off documented in `services/admin/README.md`.

- `services/auth`: added a runtime database migration runner (`src/migrate.ts`, exposed as `pnpm db:migrate:runtime` and a compiled `dist/migrate.js` in the production container image) so operators can apply Drizzle SQL migrations against the dev / prod Aurora cluster without `drizzle-kit` (which is a devDependency pruned out of the runtime image via `pnpm prune --prod`). The runner reads `DATABASE_URL` + `MIGRATIONS_DIR` from env, applies every `drizzle/*.sql` file in lexicographic order inside per-file transactions, tracks applied filenames + their sha256 in a new `__migrations` bookkeeping table for idempotency, and refuses to continue if an already-applied file's sha256 has changed (catches accidental edits of past migrations). Logs each step as single-line JSON (`{"level":"info","msg":"migration_applied","file":"0000_initial.sql"}`) for greppable CloudWatch ingestion. Migrations do NOT auto-run on auth service startup; this is operator-invoked only so schema changes never race with a rolling deploy. New `scripts/run-auth-migration.sh` wraps `aws ecs run-task` against the existing auth task definition, discovers the network config from the running service (no hardcoded subnet / SG IDs), overrides the container command to `["node","dist/migrate.js"]`, polls until the task stops, prints the container's CloudWatch logs, and exits with the container's exit code so CI / operators see green / red directly. Vitest coverage on the new runner is 100% (testcontainers Postgres, verifies fresh-apply, idempotency, hash-mismatch detection, atomic rollback on failed SQL, and non-`.sql` file filtering). `services/auth/README.md` now documents the local-dev path, the wrapper-script path, and the `__migrations` design rationale.

### Changed
- `scripts/ci-pr.sh`: scoped the pytest phase to services whose Python sources actually changed and added a hard 8-minute wallclock budget across the combined pytest run. Previously `make ci-pr` ran `pytest` for every Python service whose directory contained ANY changed file (including Dockerfile-only or README-only edits), which serialized 10+ services to ~25 minutes wallclock and blew past github.com's ~15-minute SSH idle-timeout mid-push (incident on the dockerfile-sweep PR #215). Now the script tracks two buckets per service: `PY_LINT_SET` (ruff + mypy, triggered by any in-dir change, fast <30s/svc) and `PY_TEST_SET` (pytest, triggered ONLY by `*.py`, `pyproject.toml`, `uv.lock`, or `conftest.py` changes). Infra-only, docs-only, and Dockerfile-only diffs now skip pytest entirely with an explicit log line ("no .py / pyproject / uv.lock changes in any service, skipping pytest phase"). The pytest phase wraps in `timeout ${CI_PR_PYTEST_TIMEOUT:-480}` so a runaway test cannot exceed the SSH idle budget; a 124 exit (timeout's signal) is intercepted and surfaced with an actionable message ("pytest exceeded Ns budget; relying on server-side CI for full validation. Set CI_PR_PYTEST_TIMEOUT=N to override locally"). `make ci-local` (full sweep) is unchanged and stays as the explicit "run everything" target. `CONTRIBUTING.md` updated with the new scope rules and the timeout override env-var.
- `services/admin`: refactored the SPA to read its API origin from a single `VITE_API_BASE_URL` build-time env var via a new `src/lib/config.ts` module (also exports `COST_API_BASE`, `ADMIN_API_BASE`, `AUTH_API_BASE`, and a `USE_LIVE_HEALTH_AGGREGATOR` feature flag). Endpoint constants in `src/lib/api.ts` now compose URLs against the (c+) gateway shape per ADR-038 (`/v1/cost-api/api/v1/cost/<route>`, `/v1/admin-api/api/v1/admin/<route>`, `/v1/auth/<route>`) so a production build pointed at the dev API Gateway with `VITE_API_BASE_URL=https://n2un8ica69.execute-api.us-east-1.amazonaws.com/dev pnpm build` reaches the live backend. Adds `services/admin/.env.example` (documented contract) and `services/admin/.env.development` (gitignored local defaults). README updated with the env-var contract + per-service URL composition table. New test file `tests/config.test.ts` pins the fallback defaults + the (c+) path composition so a silent regression fails CI.

### Fixed
- `infra/dev/api-gateway`: added `request_parameters = { "overwrite:path" = "/$request.path.proxy" }` on `aws_apigatewayv2_integration.service` so the `/v1/{service}/{proxy+}` route key strips the `/v1/{service}/` prefix before forwarding to the backend NLB. Without this, backend services received the full path (e.g. `/v1/auth/health`) and returned 404 because their routes are mounted at root (e.g. `/health`). Confirmed via 2026-05-10 smoke test against the auth service.
- `services/cost-api`: rewrote the `Dockerfile` so the build context is the repo root and the four sibling path-deps (`audit-lib`, `auth-client`, `middleware-lib`, `otel-lib`) are copied into a layout that mirrors uv.lock's editable `../audit-lib` style references. The existing egress rule covered the VPC CIDR (which works for interface endpoints since their ENIs live in the VPC range) but NOT for gateway endpoints. S3 gateway endpoints route packets via the route table while preserving S3's public IP as the destination, so the security group must allow that destination explicitly. Without this rule, ECR layer downloads (which fetch from S3) timed out with `CannotPullContainerError: dial tcp <S3 IP>:443: i/o timeout`. Hit on the auth service first task launch 2026-05-10.
- `infra/dev/iam`: added `kms:Decrypt` + `kms:DescribeKey` on the secrets-module CMK to every ECS task execution role's `execution_secrets` policy, scoped via `kms:ViaService = secretsmanager.<region>.amazonaws.com`. Without this grant, ECS task startup fails with `AccessDeniedException: Access to KMS is not allowed.` when pulling secret values (the execution role had `secretsmanager:GetSecretValue` but no permission to decrypt the CMK that protects the secret payload). Hit on the auth service first deploy 2026-05-10. The `kms:ViaService` condition stops this role from decrypting unrelated keys.

### Changed
- `infra/dev/api-gateway`: adopted the (c+) routing shape per ADR-038. Default routing is now a per-service proxy catch-all at `ANY /v1/<service>/{proxy+}` for every discovered service (auth, ingestion-api, summarization, notification, query-api, session-manager, billing, cost-api, admin-api), with explicit override routes layered on top when per-route policy applies. Two explicit overrides ship in this PR: `POST /v1/auth/sign-up` (5 req/sec, burst 10, anti-enumeration) and `POST /v1/auth/sign-in` (10 req/sec, burst 20, anti-brute-force). Both overrides target the same auth NLB as the catch-all but go through dedicated integrations whose `overwrite:path` is the literal stripped backend path (`/sign-up`, `/sign-in`); HTTP API v2 picks the more-specific override at request time. Per-route throttling wired via a `dynamic "route_settings"` block on `aws_apigatewayv2_stage.main` that iterates `local.explicit_overrides`. **BREAKING for direct callers of the legacy 4 explicit auth routes (`POST /auth/sign-up`, `POST /auth/sign-in`, `POST /auth/sign-out`, `POST /auth/validate`)**: those exact route keys are removed; equivalent endpoints are now reachable as `POST /v1/auth/sign-up`, `POST /v1/auth/sign-in`, `POST /v1/auth/sign-out`, `POST /v1/auth/validate` via the catch-all (or the throttled override for sign-up / sign-in). The auth service has been refactored in parallel to mount custom routes at root so the path-strip resolves correctly. New catch-alls land for `cost-api` and `admin-api` (services landed in PR #200 series). Service teams now own their public surface end-to-end: adding a new endpoint inside any service is a service-code change with zero infra PR. The legacy `local.routes` + `local.active_routes` declarative route table is removed; replaced by `local.proxy_services` (auto-derived from the discovered NLB map) plus `local.explicit_overrides` (hand-curated for policy-bearing routes only). Resource renames inside the module: `aws_apigatewayv2_integration.service` is now `service_proxy` plus a new `service_override`; `aws_apigatewayv2_route.service` is now `service_proxy` plus a new `service_override`. README updated; ADR-038 records the architectural decision.
- `services/auth`: mounted the custom routes (`sign-up`, `sign-in`, `sign-out`, `validate`, `mfa/enroll`, `mfa/verify`, `mfa/challenge`) at root instead of under `/auth/*`, preparing for the api-gateway proxy-with-overrides (c+) shape. Public callers still see clean URLs through the gateway: `POST /v1/auth/sign-up` (gateway strips `/v1/auth/` and forwards `/sign-up` to the backend). Better-Auth's own handler stays at `/api/auth/*` per SDK convention. `/health` and `/.well-known/jwks.json` were already at root and are unchanged. All 78 tests updated to the new paths and pass. Rebuild + re-push of the auth container image is required for the new ECS task to pick up the route change.
- `infra/dev/api-gateway`: flipped `var.discover_ecs_nlbs` default from `false` to `true` now that the ECS module (PR #200) has shipped and the dev ECS state file exists. Without this default flip, `terraform plan` without an explicit `TF_VAR_discover_ecs_nlbs=true` would plan to destroy the auth integration + routes that were applied via that override.
