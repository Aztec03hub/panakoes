Reading the record.

For the new desk operator

Every Tier 3 lifecycle operation produces two rows in the audit log: an intent row written before the operation runs, and an execute row written after it completes (or fails). The two rows share an aud_* request id so they can be reassembled into a single forensic event.

When the execute row is missing entirely, the intent row alone is enough to tell the next operator that the previous one tried something. That is the point of writing intent first; partial-failure visibility is not optional on a panel of buttons that can terminate live customer traffic.

The Tier3ActionIndex is a sparse global secondary index. Only rows with a non-null tier3_action attribute land in the index, so the read path here remains cheap even as the underlying audit table grows past tens of millions of rows.
